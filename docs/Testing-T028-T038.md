## 1. Overview

This document records the implementation and available verification evidence for the S3 Construction & Incident Reporting microservice.

S3 allows authenticated users to submit construction and traffic incident reports, retrieve reports within a geographic radius, and update or withdraw reports subject to ownership and moderator authorization. Public clients can retrieve non-withdrawn reports without receiving private ownership or audit information.

The service is implemented using FastAPI and PostgreSQL with PostGIS for geographic queries. It has a dedicated database and uses verified JWT claims for authenticated operations.

## 3. Implemented functionality

### 3.1 Incident submission and validation

The submission endpoint accepts authenticated reports containing:
- Incident type: `construction`, `accident`, or `other_traffic`.
- Geographic location using latitude and longitude.
- Description between 10 and 2,000 characters after trimming whitespace.
- Optional timezone-aware `observed_at` timestamp.

The service generates the incident UUID and submission/update timestamps. Clients cannot assign ownership, status, or server-managed timestamps.

An `Idempotency-Key` is required for submissions. Keys are scoped to the authenticated user and operation, retained for 24 hours, and prevent duplicate creation when a client retries the same request. Reusing a key with a different payload returns a conflict response.

### 3.2 Geographic retrieval

The public listing endpoint supports:
- Latitude and longitude as the search centre.
- A search radius greater than zero and no greater than 25,000 metres.
- Optional incident-type and status filters.
- Sorting by submission time, update time, or distance.
- Ascending or descending sort order.
- Pagination through limit and offset.

PostGIS performs the geographic filtering. Withdrawn reports are excluded from public results.

### 3.3 Authentication and authorization

S3 operates as a JWT resource server. It verifies tokens using RS256 and a configured JWKS endpoint, checking the configured issuer and audience alongside required token claims.

Authenticated users can modify or withdraw only reports they own, unless they have the configured moderator role. Authorization decisions use verified token claims rather than client-supplied identity fields.

### 3.4 Updates, status transitions, and withdrawal

The update endpoint supports changes to incident type, location, description, and status.

Supported statuses are:
- `active`
- `resolved`
- `completed`
- `inaccurate`
- `withdrawn`

New reports start as `active`. Eligible reports can transition to resolved, completed, or inaccurate, and those statuses can be reopened to active. Withdrawal is handled through the DELETE endpoint rather than a PATCH status change.

Withdrawal is a soft-delete operation. Withdrawn reports are hidden from public retrieval, while the service retains the underlying record and private audit information.

No-op updates do not change the report timestamp or create an audit entry.

### 3.5 Persistence and auditability

The service uses a dedicated PostgreSQL database with PostGIS enabled. Report changes, ownership information, idempotency records, and audit information are managed by the repository layer.

The Docker Compose configuration provides a persistent database volume. The implementation is designed to preserve report data across application restarts; a separate manual restart acceptance check is still required.

### 3.6 Health and readiness

The service exposes:
- `GET /health` for application liveness.
- `GET /ready` for readiness checks.

Readiness depends on database availability and trusted token-verification availability. A dependency failure produces a service-unavailable response rather than reporting the service as ready.
